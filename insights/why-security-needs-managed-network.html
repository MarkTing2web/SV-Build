Why Your Security System Needs a Managed Network — And What Happens When It Does Not

Most security system failures are not camera faults or alarm faults. They are network faults — loops that take down an entire site, unmanaged switches that starve cameras of bandwidth, and flat networks where a compromised device can reach everything else. Wee Meng explains how Securevision designs the network foundation that security systems run on.

Ler Wee Meng · Founder, Securevision BEng (NUS) · LLB (UOL) · years in Singapore security Updated June 2026 · 12 min read

When a client calls to say their cameras have gone offline, the first question I ask is not "what model is the camera?" It is "what switch are the cameras connected to, and can you tell me if the switch is still powered?" In most cases, by the time I have asked that question, I have already logged into our cloud management platform and I can see the answer.

That is the difference between a security system built on a managed network and one built on an unmanaged one. One I can see and fix remotely in minutes. The other requires a site visit, a physical inspection of every device, and a process of elimination that takes hours.

The network is the foundation that every camera, access control reader, intercom, and alarm communicator runs on. It is also, in my experience, the most under-specified part of most security installations. Many integrators focus on the cameras and the NVR — the visible parts — and treat the network as an afterthought. A cheap unmanaged switch from an electronics shop does the job in the short term. Until it does not.

This article explains how Securevision thinks about network infrastructure for security systems — why we specify managed switches, what VLANs do and why they matter, how remote management changes the way we support clients, and what happens in the field when any of these things are done wrong.

Managed vs Unmanaged Switches — What Is the Difference?

An unmanaged switch is a passive device. You plug in cables, power it on, and it forwards traffic between connected devices. There is no configuration, no visibility into what is happening on each port, no ability to segment traffic, and no remote access. It works. Until something goes wrong — and then it gives you nothing to work with.

A managed switch is configurable. You can set up VLANs to isolate different types of traffic. You can configure MAC address security on each port so only authorised devices can connect. You can monitor bandwidth per port and see which devices are online or offline. You can remotely reboot a stuck device without physically touching it. And you can do all of this from anywhere in the world through a cloud management platform.

For a home with four cameras, an unmanaged switch is often sufficient — the scale is small, the risk is manageable, and the cost of a managed switch may not be justified. For anything larger — a commercial property, a condominium, a school, a multi-building site — the case for a managed switch is clear. The ongoing operational benefit outweighs the upfront cost difference, usually within the first year of operation.

The Cost Comparison

The price difference between an entry-level unmanaged PoE switch and a comparable managed PoE switch with cloud management is typically SGD 80–150 for an 8-port unit. On a 30-camera project with three switches, that is SGD 240–450 additional cost. Weighed against a single site visit to diagnose a network fault — typically SGD 150–300 in labour plus travel time — the managed switch pays for itself the first time something goes wrong remotely fixable.

VLANs — Why Every Security Network Should Have Them

VLAN stands for Virtual Local Area Network. Without going into the technical detail, a VLAN divides one physical switch into multiple isolated logical networks. Devices on different VLANs cannot communicate with each other unless traffic is explicitly routed between them at a Layer 3 switch — which Securevision controls.

On a security system deployment, this solves three distinct problems.

Problem 1: Broadcast Flooding

Every device on a network periodically sends broadcast traffic — messages addressed to all devices on the same segment. On a flat network with 30 cameras, 20 access control readers, 10 intercom stations, and 5 office computers all on the same switch, every broadcast from every device reaches every other device. With 65 devices each sending regular broadcast traffic, the background noise is significant. It consumes switch processing capacity and competes with the actual camera recording traffic that the network exists to carry.

VLANs confine broadcast traffic to its own segment. Camera broadcasts stay on the camera VLAN. Access control traffic stays on the access control VLAN. Each segment is smaller, quieter, and more efficient.

Problem 2: Cross-Contamination

A misconfigured or faulty device on a flat network can affect every other device on the same segment. The most common version of this is a broadcast storm — a device, or a network loop created by accidentally connecting two ports together, starts generating broadcast traffic at an abnormal rate. On an unmanaged flat network, this traffic floods every device on the switch simultaneously. Within seconds, cameras stop recording, access control readers stop responding, and the entire security system goes offline.

On a properly segmented VLAN network, a storm on the camera VLAN does not reach the access control VLAN. The access control system keeps running. The VLAN boundary is a firebreak.

Real Example — The Loop That Took Down a Site

We were called to a commercial property where the entire CCTV system had gone offline during a routine maintenance visit by a third-party contractor. When we investigated, we found the contractor had accidentally connected two ports on the same unmanaged switch together — creating a network loop. On an unmanaged switch with no storm control, the broadcast storm that resulted flooded every port within seconds. All 24 cameras went offline simultaneously. The entire network had to be powered down and restarted. On a managed switch with storm control, the switch would have detected the loop, isolated the offending port, and sent an alert — without taking down the rest of the network.

Problem 3: Unauthorised Access

A flat network without VLAN segmentation means that anyone who physically connects a device to a camera port on a patch panel has potential access to the entire network — including the NVR, the access control server, and any other connected system. In a building where patch panels are in accessible locations — riser cabinets, false ceilings, carpark comms rooms — this is a realistic risk.

VLAN segmentation restricts each port to its designated network segment. A camera port can reach other cameras and the NVR. It cannot reach the access control server, the management workstation, or the building's IT network. This is the same principle as physical access zoning applied to the network layer.

Securevision Standard

On all managed network deployments, Securevision applies VLAN segmentation as a baseline — CCTV cameras on one VLAN, access control readers on a second, intercoms on a third, management traffic on a fourth. Even for relatively small commercial sites, the segmentation takes 30 minutes to configure and provides protection that unmanaged flat networks cannot offer. We do not treat this as optional.

MAC Address Port Security

Every network device has a MAC address — a unique hardware identifier built into its network interface card. No two devices share the same MAC address. Managed switches support a feature called MAC address binding, or port security, which ties each switch port to the specific MAC address of the device authorised to connect to it.

In practice: each camera port on the switch is configured with the MAC address of the camera connected to it. If a camera is removed and a laptop is plugged into the same port, the switch detects the MAC address change, disables the port immediately, and logs the event. The laptop gets no network access. The security team gets an alert.

This is a practical security measure for any installation where switch ports are physically accessible. Comms rooms in condominiums, riser cabinets in commercial buildings, patch panels in false ceilings — these are not always under lock and key. MAC address port security ensures that physical access to a port does not translate to network access.

It also has an operational benefit: if a camera fails and is replaced with a different unit, the switch will reject the new camera until the MAC address binding is updated. This creates an audit trail — every device substitution requires a deliberate configuration change, which prevents undocumented hardware swaps that can create future troubleshooting confusion.

Remote Management — What It Actually Means in Practice

Both Ruijie/Reyee and TP-Link Omada — the two switch platforms Securevision deploys — provide cloud-based management through their respective platforms (Ruijie Cloud and Omada SDN). Every switch, access point, and wireless bridge connected to the platform is visible from a single dashboard, regardless of where it is physically located.

What this means in practice for a Securevision client:

When a camera goes offline, Securevision logs into the cloud platform, locates the switch the camera is connected to, checks whether the switch port is showing a link, and determines whether the issue is the camera itself, the switch port, or the switch's network connectivity. In most cases, this diagnosis takes under five minutes. If the issue is a stuck camera that needs a power cycle, we can remotely disable and re-enable the PoE port on the switch — effectively rebooting the camera without anyone going on site.

When a client asks "is everything working?", the answer is available immediately — device count online, bandwidth per port, any alerts or warnings flagged by the system. This is the kind of operational visibility that previously required on-site inspection or expensive network monitoring software.

When Securevision needs to make a configuration change — adding a new VLAN, adjusting port settings, updating firmware — this can be done remotely. The client does not need to schedule an engineer visit for tasks that take five minutes on the cloud platform.

Client Access Control

Ruijie Cloud and Omada SDN both support a permission model where the client owns the account and controls who has access. When Securevision needs to log in to assist with a fault or configuration change, the client grants temporary access — with a time limit that they set. Once the window expires, Securevision's access is automatically revoked. The client's network remains under their control at all times. This is particularly important for government-related buildings, financial institutions, and data centres where ongoing third-party access to network infrastructure is a compliance concern.

PoE — Powering Security Devices Over the Network Cable

PoE stands for Power over Ethernet. A PoE switch delivers both data and electrical power through the same network cable — no separate power supply needed at each camera, access control reader, or intercom station. This is the standard configuration for all Securevision deployments.

The practical implications are significant. A 30-camera installation with non-PoE cameras requires 30 individual power adapters at 30 camera locations. With PoE cameras and a PoE switch, all power is managed centrally from the switch. If a camera needs to be rebooted, the power to that specific port can be cycled remotely. If the switch is connected to a UPS (uninterruptible power supply), all cameras continue operating during a power outage without any additional UPS units at each camera location.

PoE standard matters. 802.3af (PoE) delivers up to 15.4W per port. 802.3at (PoE+) delivers up to 30W per port. PTZ cameras, intercoms with displays, and certain AI-capable cameras require PoE+. Specifying the wrong PoE standard is a common mistake on projects where a mix of standard and high-power devices is connected to the same switch — some devices will not power on, and the fault is not immediately obvious.

When Cables Are Not Possible — Wireless Bridges

There are two scenarios we encounter regularly where running a data cable is either impossible or prohibitively expensive: connecting cameras across a road or between separate buildings, and installing a camera inside a lift car.

Cross-building surveillance: A car park across the road, a guard post at a separate building entrance, a perimeter camera mounted on a boundary wall outside the main building — all of these need to connect back to the NVR inside. Running cable underground across a road requires permits, civil works, and significant cost. A point-to-point wireless bridge — one unit mounted at each end, aimed at each other — creates a wireless Ethernet link that carries the camera feed back to the control room. We have deployed this at a large multi-building commercial development in Singapore, carrying feeds from cameras across a road and through a park back to the central control room. The link has been reliable since commissioning.

Lift car cameras: Running a data cable from a camera mounted inside a lift car to the motor room at the top of the shaft involves flexible conduit, continuous flex cable rated for vertical travel, terminations that survive tens of thousands of door cycles — and a significant labour cost. A wireless bridge pair removes all of this: one small unit inside the lift car, one in the motor room, both aimed at each other through the shaft. The camera feed is transmitted wirelessly up the shaft. We have deployed this configuration in multiple Singapore condominiums. It is reliable, cost-effective, and significantly faster to install than a cabled alternative.

The bridge equipment we use (Reyee RG-EST series) is factory-paired — the two units are configured to connect to each other out of the box. There is no wireless configuration to perform on site. Power both units, mount them, and the link is up within minutes. Both units are visible on the same Ruijie Cloud dashboard as the rest of the network infrastructure.

IP Address Planning — The Detail Nobody Thinks About Until It Causes a Problem

Every device on a network has an IP address. In a security system, that means every camera, every NVR, every access control reader, every intercom station, and every switch management interface. How those IP addresses are assigned and organised affects how easy the system is to manage, troubleshoot, and expand.

The most common mistake is assigning a small subnet to a security network that will eventually grow. A /28 subnet gives 14 usable IP addresses. Sufficient for a 10-camera system. Not sufficient when the client adds 8 cameras the following year and another 10 the year after. Renumbering a live security network — reassigning IP addresses to devices already in service — is disruptive, time-consuming, and unnecessary if the network was sized correctly at the outset.

Securevision assigns subnets with deliberate headroom. A 30-camera installation gets a /24 subnet — 254 usable addresses. The system uses 30 of them today. When the client doubles their camera count in three years, there is no renumbering. The network accommodates the growth without redesign.

We also use consistent IP address schema across the same deployment — cameras in one range, NVRs in another, access control in a third. When we log into a site remotely and need to identify a specific device quickly, a logical address scheme means the device is where we expect it to be. This sounds like a minor detail. In a fault situation at 2am, with 200 cameras and a client waiting for their system to come back online, it is not minor.

Switch Stacking — For Larger Deployments

On large security projects — a site with 200 cameras and 50 access control points, for example — a single switch cannot provide enough ports. The traditional solution is to use multiple switches connected to a core switch via uplinks. This works, but each switch is managed as an independent device, and bandwidth between switches is limited to the uplink port capacity.

Switch stacking takes a different approach. Two or more physical switches are connected via dedicated high-speed stack ports and present to the network as a single logical device. From the management platform, a 2-unit stack of 48-port switches appears and behaves as one 96-port switch. All 96 ports share the combined switching capacity of both units. Traffic does not need to travel over an uplink between switches — it is switched internally at full speed.

For a site like the large commercial project we deployed with close to 200 cameras, the practical benefit of stacking is load distribution. The CCTV network generates heavy, continuous traffic — 4K cameras recording 24/7. The access control network generates light, intermittent traffic — a burst when someone badges through a door, then silence. On a stacked pair, the combined bandwidth pool is available to whichever network needs it. Under peak CCTV load, the access control traffic is handled without competition. This reduces congestion faults that on a non-stacked network would require either upgrading individual switches or accepting degraded performance.

The TP-Link Omada stackable L3 switches support up to 4 units per stack in controller mode. We have used this specifically for large-scale CCTV deployments in Singapore where the camera count and distribution pattern makes stacking the most cost-effective architecture.

The Network Is Not an Afterthought

Every camera, every reader, every intercom, every alarm communicator in a modern security system is a networked device. The network is not ancillary infrastructure — it is the system. When the network fails, the security system fails. When the network is poorly designed, the security system performs poorly.

The difference between a managed and unmanaged network, between a VLAN-segmented deployment and a flat one, between a cloud-monitored infrastructure and one that requires a site visit to diagnose — these differences translate directly into system uptime, response time to faults, and the ability to support clients effectively after installation.

When Securevision designs a security system, the network design starts at the same time as the camera layout and the access control zoning plan. It is not something we figure out later. The switch specification, the VLAN plan, the IP addressing scheme, and the remote management configuration are part of the deliverable — not an addition to it.

Securevision View

If you are evaluating security system proposals and one does not include a managed switch specification with a VLAN design, ask why. The answer will tell you something important about how the integrator thinks about long-term system reliability — and about what your experience will be when something eventually goes wrong at 2am and you need a quick answer.
